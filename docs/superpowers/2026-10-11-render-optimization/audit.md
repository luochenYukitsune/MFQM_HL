# 全代码渲染评估

已逐文件阅读 145 个主 Java 源文件（50 个客户端、95 个其他模块）、13 个原有 Java 检查程序及新增几何微基准、全部 27 个 Python/PowerShell 工具，以及 Gradle 构建、启动包装脚本和 metadata。完整读取清单见 [主审覆盖](main-read-coverage.txt)和[辅助覆盖](auxiliary-read-coverage.txt)。搜索用于定位，输出截断的代码另行补读；依赖缓存、先前导出副本和二进制不属于本项目手写源码。

## 主要开销与本次处理

黏丝有实体厚度、端帽和贴肤裁剪，每根会生成若干四边形。原来先生成一份完整网格，再逐面裁剪四个顶点并生成另一份网格，相邻面重复处理同一个环顶点。本次每环顶点只裁剪一次，直接生成最终四边形，同时保持原始环用于绕序判断。独立旧实现比较确认顶点、法线、颜色、面序完全相同。默认密度、随机种子、透明度、皮肤附着和介质内根部均沿用原规则。

每连接提取内复用插值实体位置；纹理四边形不再创建四元素顶点数组。服务器每 tick 的单连接有效性原来调用完整聚合器，产生单元素列表、64 元素力数组与结果对象，本次直接复用原 `forceFor` 判断，最终全连接求力仍由原聚合器执行。这项改动减少集成服务器和专用服务器的垃圾分配，对 GPU 绘制量没有影响。

## 已有机制应继续保留

- `AdhesiveFeetSampler` 已按实体、tick、partialTick 缓存双脚采样，限制缓存规模并用弱引用区分实体；不应再为每根黏丝新建模型。
- `AdhesiveDisplayBudget` 已每目标每 tick 复用一次连接选择，限制搜索结果和缓存，密度变化不增加物理实体。渲染结束后使用不可变几何快照，不能让延迟回调引用会被复用的 State。
- 胶膜蒙版、网格、平面纹理和皮肤资源已有有限容量缓存，并处理资源重载与纹理销毁。3D Skin Layers 的注入网格可随可见性、设置和姿态变化；将其永久缓存会破坏贴肤效果。
- 根实体的包围盒很小，黏丝能从它延伸到角色，故不能直接启用只依据根盒的视锥裁剪。FirstPersonModel 的相机脚部坐标必须按当前帧重新采样；光影阴影 pass 的排除逻辑保持原样。
- 蜜蜂、blob、留靴和机关等沿用模型／物品渲染器；气泡尺寸已有严格限幅，本轮没有扩大粒子或改变原有透明绘制层。

## 预计算皮肤面为何未采用

试验实现与旧算法的 8,192 条随机射线及边界情况精确等价。它在 256 条查询的复杂面上测得约 9%～18% 查询耗时改善，但 32 条查询增加约 2%～8% 耗时，每个新姿势仍为所有面创建系数对象。懒初始化避免干地计算，却不能解决低密度的初始化成本。最终撤回 Prepared、Foot API 和相应测试，保留原查询和缓存。实验 CSV 留作评估依据，未纳入交付功能。

## 仍然存在的性能成本

GPU 半透明叠加与顶点提交仍是大密度下的重要成本。六段黏丝最多 48 个四边形，512 根约 98,304 个顶点；8192 根按现有三段策略最多约 983,040 个顶点，实际会因淡出、裁剪退化面而减少。数量上限由用户选定，本轮不会通过减少密度或取消厚度来制造性能提升。

进一步优化宜先采集真实场景的 CPU/GPU 帧时间，再考虑跨连接批量几何或距离细节分级；这会涉及第一人称延迟绘制、阴影 pass 和透明排序，应作为单独改动验证。服务端碰撞形状常量、反应标签常量和局部 BlockState 复用是低风险候选，详见[辅助审查](review.md)；本次未顺带改变世界生成、运动预测或网络节奏。

本次微基准只证明几何生成路径更省计算和分配，不能给出整机 FPS 的提升百分比，也不代表重测了所有光影包。
